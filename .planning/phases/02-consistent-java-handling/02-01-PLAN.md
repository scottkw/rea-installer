<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| inherited environment -> installer | `JAVA_HOME` and `JAVA_TOOL_OPTIONS` come from the user's shell and are untrusted input |
| `$JAVA_HOME/bin/java` -> installer | the script executes a binary at a user-supplied path and parses its output |
| installer -> shell profile | the profile block is executed by every future shell the user opens |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | Linux profile block `JAVA_HOME` line | medium | mitigate | Only `setting JAVA_HOME "$STATE_DIR/jdk"` writes it; the user's value is never copied into `profile_lines`; uninstall's block removal undoes it |
| T-02-02 | Information disclosure | `jdk_usable` captured output | medium | mitigate | `$out` is matched with `[[ =~ ]]` and never printed; the D-04 warning names only the folder (a `Picked up JAVA_TOOL_OPTIONS:` line can hold `-Dhttp.proxyPassword=`) |
| T-02-03 | Elevation of privilege | executing `$JAVA_HOME/bin/java` | low | accept | The script runs as the user; only package-manager calls go through `sudo_cmd`, and `sudo` resets the environment by default; no `eval` of the output |
| T-02-04 | Repudiation | too-old or broken JDK reported as "Done" | medium | mitigate | `jdk_usable` fails closed (missing, non-executable, non-zero exit, unparseable); post-install `jdk_usable "$STATE_DIR/jdk" || die` |
| T-02-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package installs; the Adoptium download and its published-checksum check are unchanged |
</threat_model>
